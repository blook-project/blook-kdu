# Changelog

All notable changes to blook-kdu are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses
[Semantic Versioning](https://semver.org/).

## [1.1.1] - 2026-10-22

- **Fixed: the 1.1.0 package shipped a CLI without the payload backend.**
  `payload_blob.h` is generated by `kdu_payload`'s `after_build`, but `kdu_ipc`
  (`#include`s it behind `__has_include`) could be compiled before that header
  existed: xmake compiles the sources of unrelated targets in parallel
  (`build.across_targets_in_parallel`). On a clean build tree - i.e. CI, which
  is what produced the published 1.1.0 zip - this yielded a `kdu.exe` whose
  `payload` commands answered "this build has no payload backend (needs
  blook-kchannel and blook-drv-lite)" while `bin/kdu_payload.sys` was still
  shipped. Incremental local builds hid the race because the header was
  already on disk.
- `kdu_payload` now sets `build.fence`, so every target that depends on it is
  only compiled after the payload image and its blob header exist.
- `kdu_ipc` is built with `KDU_EXPECT_PAYLOAD`: a missing `payload_blob.h` is a
  compile error instead of a silently backend-less CLI.
- `scripts/package.ps1` verifies that the embedded drv-lite image is present in
  `bin/kdu.exe` and refuses to write a release zip otherwise.

No exploit behaviour changed; `kdu.exe` from 1.1.1 is byte-identical in
function to a correctly built 1.1.0 plus the payload backend.

## [1.1.0] - 2026-10-22

- **Lab verification**: 50 of the 140 bundled exploits are verified usable in the signed VMware lab guest (Windows 11 build 26200): 36 memory-primitive drivers pass `kdu exploits test`, 14 kill-only drivers terminate a PPL-protected process through `kdu process kill`. Per-id lists, environment and documented not-usable drivers: `docs/lab/RELEASE-VERIFICATION.md`.

The exploit catalogue was expanded from 16 to **140 exploits**, split into
**118 memory-primitive drivers** (arbitrary physical or kernel-virtual
read/write, or a physical map that the shared page-table walker turns into VA
access) and **22 kill-only drivers** (PPL/EDR termination, no memory primitive).
Every exploit is an independent module with a mock-device unit test, and the
memory exploits are validated end-to-end against real drivers in a disposable
VM (`docs/lab/`).

- Exploit coverage: recent BYOVD CVEs from 2023-2026 (CVE-2023-20598,
  CVE-2023-52271, CVE-2024-51324, CVE-2025-1055/52915/61155/70795, CVE-2026-8501,
  ...), the classic KDU catalogue (ASRock/ASUS/AMD/Dell/HP/Lenovo/NVIDIA/
  Realtek/MSI/Razer/... hardware-access drivers), and several undocumented
  drivers turned into first-class exploits (`ktapi` fail-open HAL physical map,
  `truesight` VA r/w, `astra64` physical map, `winhwdrv`, `asrdrv109`,
  `sysdrv3s`, ...).
- Catalogue top-up: 19 further WinIO/WNBIOS/GLCKIO2/physmem builds
  (`winio_64a`, `winio_64b`, `winio_a_nz`, `winio_b`, `winio_w`, `winio_edr`,
  `winio_elan`, `winio_ew1`, `winio_ew2`, `winio_heaven`, `winio_tk`,
  `winio_ufu`, `wnbios_v1`, `wnbios_v2`, `physmem_v2`, `glckio2_v1`, `asmio`,
  `winio_big1`, `winio_big2`) ship as independent modules with mock-device unit
  tests and their own CI jobs. They were added after the lab matrix, so the 50
  verified ids are the verified subset of the 140 bundled exploits.
- New `Capability::process_kill` and `IDriverInterface::terminate_process()`:
  kill-only drivers are honest about having no memory primitive, are skipped by
  `kdu exploits test` (`SKIP`, not FAIL) and are driven by the new
  `kdu process kill --pid <pid> [--exploit <id>]` command.
- New `BLOOK_KDU_DRIVER_DIR` override: the service host loads
  `<dir>\<driver_file>` instead of the embedded RCDATA image when set. The VM
  lab re-signs drivers for test signing and uses this to exercise the bundled
  binaries without changing the shipped bytes. `ExploitInfo::device_name` also
  accepts ';'-separated alternatives now.
- New tooling: `scripts/new-exploit.ps1` (scaffold + resource id allocation),
  `scripts/clone-exploit.ps1` (driver variants), `scripts/dev-build.ps1`
  (parallel-safe serialized build), `scripts/vm-lab.ps1` (VM matrix over a
  bvmenv guest: sign, stage, run `kdu exploits test`, matrix.json/matrix.md,
  crash reset, resumable), `tools/driver-intel` (pefile+capstone static
  recovery of devices/IRP dispatch/IOCTLs/primitives plus a corpus ranking) and
  `docs/adding-exploits.md` (the exploit contract).
- Corrected four 1.0.x exploits whose IOCTL translation did not match the
  shipped binaries: `physmem64` (WinIO-style map/unmap), `directio64`,
  `dbk64` and `gmer`.
- Safety: WinRing0-family drivers (`winring0`, `hwrwdrv`, `winhwdrv`, and other
  `unsafe_physical_holes` modules) keep physical read/write but page-table based
  VA/process access is opt-in (`BLOOK_KDU_ALLOW_UNSAFE_PHYSICAL=1`) because a
  failed `MmMapIoSpace` in that family is dereferenced and can hang/bugcheck the
  machine. Low-stub PML4 discovery now probes the 8-byte jump signature before
  reading a full page, making byte-granular physical drivers ~500x cheaper.
- `docs/exploits-rejected.md` records drivers that the static analyzer
  initially flagged but that turned out to have no memory primitive; they are
  intentionally not shipped as fabricated exploits.

## [1.0.2] - 2026-10-21

- Payload backend replaced with **blook-drv-lite** (pinned source drop): kernel
  VA/physical read-write, CR3 process read/write, module list/dump, handles,
  DSE and (where supported) InfinityHook. The payload can be loaded through the
  manual mapper or, on builds where mapped images cannot execute, through the
  drv-lite **service path** (bootstrap in `Parameters\Bootstrap`). `kdu payload
  load` loads it standalone and runs a full client self-test (no vulnerable
  driver needed).
- 8 more exploits (16 total): `gmer`, `kph`, `mimidrv`, `amd`, `directio64`,
  `lha`, `tpw`, `msio64`, each with its own mock unit test and per-exploit CI
  job.
- Removed the VMware-only execution guard: `kdu_open()` no longer refuses to run
  outside a VMware guest. The e2e harness still uses a disposable VM.
- Embedded vendor drivers are shipped **as-is** (no Authenticode stripping and
  no re-signing in CI); only the toolkit's own payload/test images are signed
  locally with the SPC signer (SHA-1 + TSA root trust) for service loading.
- CI now runs real kernel code: `kernel-load-smoke` builds a minimal SPC-signed
  driver, verifies `/kp`, starts it (`STATE 4 RUNNING`), runs an IOCTL client
  (magic + kernel pointer) and uploads `ci-e2e-result.json` (cases[] with
  pass/fail/skip, allowed skip vocabulary, runner testsigning + `/kp` facts).
  Registered-driver/mapper cases stay VM-only and are recorded as skips.
- Per-exploit CI isolation: one build/test job per exploit (16 exploits / 18
  jobs including build and kernel load), generated from the directory layout.
- CI hardening: guarded `sc create/start` and client calls with hard timeouts,
  and the cleanup step always exits zero so a deleted test service cannot fail
  the job.
- `kdu payload load --mode auto|manual|service [--unsigned-driver ...]` and the
  `MapOptions::PayloadLoadMode` SDK enum.
## [1.0.1] - 2026-10-21

- Package the CLI (`bin/kdu.exe`) again: the release workflow now prepares the
  signed embedded-driver assets before building, so the `kdu` target cannot be
  silently skipped after a clean configure (the 1.0.0 zip only contained
  `kdu_payload.sys`).
- Reproducible clean builds: `scripts/prepare-assets.ps1` runs in the `kdu`
  target's `before_build`, so `xmake f -c -y -m release && xmake -y` works from a
  fresh clone without a separate prepare step.
- VM e2e provenance: `summary.json` records `bvmenv_version` and
  `bvmenv_sha256` (safe bvmenv build), and evidence was regenerated with the
  v1.0.1 binaries.
## [1.0.0] - 2026-10-21

First release. Highlights:

- Self-contained user-mode CLI + SDK that stages bundled vulnerable drivers,
  optionally follows up with a manual-mapped kernel payload over blook-kchannel
  (pinned `40a5337`), and cleans up the driver/service/registry at exit.
- 8 exploits with per-exploit mock unit tests and independent CI jobs:
  `asrock`, `atszio64`, `dbk64`, `echodrv`, `gdrv`, `physmem64`, `rtcore64`,
  `winring0` (decompressed, Authenticode-stripped and re-signed at build time
  with the bundled test signer).
- Memory: physical and kernel-VA read/write, translation, CR3 process memory
  (mref.cc technique), module enumeration, driver dumping, JSON batch runner.
- DSE status/disable/restore API via `g_CiOptions`, ACPI-style victim-driver
  manual mapper for the payload, blook-kchannel IPC, trace scanning and cleanup.
- Safety: the SDK refuses kernel operations outside a VMware guest; the e2e
  harness refuses non-VMware guests and hard-times every bvmenv call.
- Real VM evidence committed under `docs/evidence/20261021-e2e-vm/`
  (Windows 11 26200): 28 checks, 0 failed, 10 documented skips.

Known limitations on Windows 11 26200 (documented, gated in the e2e suite):

- The mapped payload image cannot execute from kernel pool
  (`ATTEMPTED_EXECUTE_OF_NOEXECUTE_MEMORY`); the mapper stage runs but the
  payload needs a PTE-NX-clear pass or a service+kchannel loading mode.
- Four bundled driver images (`atszio64`, `echodrv`, `gdrv`, `physmem64`) are
  rejected by Microsoft's vulnerable-driver blocklist (CERT_E_REVOKED); they are
  recorded per exploit as platform-blocked.
- `dse/disable` is not exercised by the automated suite on this build (patching
  `g_CiOptions` no longer gates driver loads there).
## [Unreleased]

### Added

- `kdu batch <ops.json>`: one-session, JSON-described multi-operation runner
  (read/write physical/virtual/process, translate, CR3, DSE, modules, sleep)
  with `--continue-on-error` and structured results; documented JSON schema.
- Documented stable CLI exit codes and `--json` output schema
  (`docs/json-schema.md`).
- `examples/api_example.cpp`: 20-line SDK walkthrough, documented in
  `docs/api.md`.
- Manual mapper hardening: /GS security-cookie randomization (detect + patch
  cookie/complement), exception-directory detection, strict import/relocation/
  section bounds validation, and host unit tests for malformed/truncated images
  and cookies.
- VM-only safety gate: the SDK refuses kernel operations outside a VMware guest
  (no override), the guest e2e runner refuses non-VMware guests, and the host e2e
  script requires `-Vm` plus hard timeouts on every `bvmenv` call.
- Six more exploits (asrock AsrDrv107n, winring0, physmem64, dbk64, atszio64,
  echodrv) with per-exploit mock unit tests and automatic per-exploit CI jobs.

- Public SDK (`include/blook/kdu/kdu.h`): session object, status/error type,
  physical/kernel-virtual/process memory access, DSE control, module
  enumeration, driver dumping, payload map/unmap, cleanup and trace scanning.
- Exploit abstraction (`IExploit`, `IDriverInterface`, `IKernelAccess`,
  `IServiceHost`, `IDeviceIo`) with dependency injection for unit tests.
- Exploit registry generated from `src/exploits/*` and per-exploit CI jobs.
- First exploits: GIGABYTE GDRV (CVE-2018-19320) and MSI RTCore64
  (CVE-2019-16098), each with its own embedded, staged-at-runtime driver image.
- Driver loading from memory: embedded RCDATA image, temporary file, service
  create/start, device open, automatic stop/delete/cleanup.
- x64 page-table walker (4 KiB/2 MiB/1 GiB pages), low-stub PML4 discovery,
  CR3-based process memory access with PEB validation (mref.cc technique).
- DSE: symbol-free `g_CiOptions` resolution in `ci.dll`, status/disable/restore.
- Manual mapper: image preparation (sections, imports, relocations), kernel
  stage bootstrap, arbitrary `.sys` mapping and payload bootstrap.
- Kernel payload driver (WDK, C++17, manual-mappable) with the complete RPC
  protocol over blook-kchannel.
- blook-kchannel adapter (single translation unit, source-drop integration).
- CLI (CLI11/fmt/spdlog/nlohmann_json): `info`, `exploits list|probe|test`,
  `mem phys|virt|process read|write|dump`, `map`, `unmap`, `unload-payload`,
  `dse status|disable|restore`, `modules`, `dump-driver`, `doctor`, `traces`,
  `cleanup`, `--json`.
- Unit tests (doctest): page tables, EPROCESS helpers, Win32 helpers, exploit
  metadata/IOCTL encoding per exploit.
- GitHub CI: main build (user + payload with pinned blook-kchannel and WDK),
  host unit tests, clang-format check, registry/version consistency, release
  packaging; per-exploit matrix jobs.
- Release workflow with canonical `blook-kdu-<version>-windows-x64.zip` +
  `.sha256` assets and a package-registry manifest/publish script.
